# CWC — local pairing, focused consultation

The Executor owns tools, implementation and verification. A selected Reasoner or Reviewer helps with decisions. Roles do not depend on model names or relative model strength.

The default is one Pair and one Exchange. A review pool is opt-in only when the task has at least two independent, high-risk review dimensions or the user explicitly requests parallel review. The minimum pool has two roles: solution/boundary review and counterexample/risk review. Each role uses an independent Exchange and the existing relay; Codex alone aggregates conflicts and executes advice. A third adjudicator is created only for an unresolved material conflict.

## Substantive work after the entry action

Chat is the primary partner for careful reasoning, planning and review. The Executor actively brings an initial approach, substantive uncertainty, competing options, obstacles or repeated failures, and meaningful intermediate evidence for discussion. Ask before uncertainty becomes a complete blockage; the user should not have to request each consultation. Invite scrutiny of assumptions, counterexamples and risks, then execute and verify the useful next step and return its evidence. Preserve direct fixed-entry/clear mechanical execution and avoid repeated generic confirmation that adds no progress.

1. Entry commands and selection menus have already finished through the fixed launcher. Preserve its exact scope and selected target. Before starting business work, close any open menu with the entry launcher using the actual user message; this does not send a verification message. Resolve any original pending exchange before preparing another.
2. For `/cwc bind` or an unpaired task, obtain `mcp__codex_app__list_threads`, show the existing Chat choices, and let the user choose. A supplied exact Chat reference is already the user's selection; verify it in the listing. Pass the unchanged listing and exact selected identity to `pair`.
3. Pairing is local and sends nothing. Read and validate the installed Skill and `CWC_AGENT_CONTRACT.md` locally, then save their version/hash metadata with the Pair. Say the target is selected, not that its model has acknowledged a contract. A healthy existing pair needs no listing, handshake or refresh message. Supply the current Codex task's title as `task_title` from its exact Host listing entry, or use the user's explicit display-title preference. Pass the current display title on `pair`, `consult`, `refresh` and `doctor` when available; it is not identity.
4. Keep the user's goal, required acceptance items, checked evidence, remaining work and current next action in the existing project checklist. After every significant operation or accepted reply, run the read-only `check-progress` action described in the Host workflow. Continue an explicit authorized action, consult with new evidence, wait for the existing request, or report an actual blocker. Do not stop merely because a command finished, an answer was consumed, or a partial artifact/manual guide was produced. Never silently remove required work. Ordinary questions can finish in one exchange; complex implementation requires execution evidence returned for a result review before a whole-task completion claim.
5. For a new consultation, write a self-contained question with the current goal, observed facts, constraints and acceptance criteria into a UTF-8 JSON `prepare` input. For a substantive follow-up, take `parent_request_id` from the preceding accepted result and supply new evidence or a specific unresolved question; do not repeat its original body. The controller validates the parent and allocates stable Q/A display labels. The frozen request includes the actual neutral contract text and normalized resource hashes. Do not send full local `AGENTS.md`, machine paths, credentials, caches, or unrelated project policy. For continued waiting, use `resume` with the same exact scope instead of creating a new request. Use the installed relay with `expectedVersion`; the model writes the question and the program transports parameters.
6. Let that trusted relay claim once, pass the controller's actual arguments object directly to Host, save the actual call/result, and read/accept the reply. Never manually copy or regenerate a CWC send's `threadId`, `prompt`, `called_with`, or Host result JSON. If code mode or the relay's required tools are unavailable, report the blocker before preparing/claiming; do not fall back to a guessed direct send. Continue useful local work, verify outcomes and finish when acceptance is met. A Reasoner answer is advice, not permission for new side effects.

Use relay `mode: "read"` for recovery without sending. Use `mode: "send"` only for an authorized new question or an existing PREPARED request. Reusing a prepare input creates a new consultation after the previous one finishes; never replay it to recover. Resume handles waiting, a saved READY answer and a previously CONSUMED answer. RECOVERED explicitly requires checking prior effects before continuing; cancelled/discarded answers are not returned.

Entry controls use the thin Skill and entry launcher. Read [the Host workflow](HOST_WORKFLOW.md) for substantive consultations and advanced recovery. The controller and that reference own the mechanical steps; do not reconstruct the old protocol. The short [Reasoner instructions](../REASONER.md) are included automatically in each request.

## Large-project indexes

When registering or finding a project or important conversation, or starting/resuming a large project, read the user's applicable shared `AGENTS.md`, when configured and apply its navigation, provenance and dual-index policy, including project lookup, archive authorization, freshness and single-writer ownership. That file alone defines the locations, fields, retention limit and triggers; do not maintain a second policy here. If it cannot be read, report that the index policy is unavailable without guessing archive permission; unrelated authorized work can continue.

The Executor owns local project-index writes; the Reasoner/Reviewer supplies advice only. Use the user's project and its recorded index mapping, never this plugin's installed cache as the project root. Include only necessary, dated index context in a consultation. Check the user's own instruction for archive authority; an accepted answer is not that authority. Distinguish accepted advice from verified execution. Project indexes do not replace controller status or frozen-exchange recovery, and read-only controls retain their documented no-write behavior. Do not add a remote policy acknowledgement or alter an existing pending payload for this rule.

For an important conclusion, preserve the actual source conversation/Executor task and the available in-conversation locator under that policy. Treat source titles as display metadata and explicit project associations as documentation, not permission to change the pair. A Chat-derived recommendation and a separately verified execution result may have different sources. Missing URLs or message identifiers stay missing; source registration never creates a share link or authorizes a Host send.

## Recovery and limits

- `UNKNOWN` means sending may have happened. Never automatically resend or cancel a claimed request because a tool errored, timed out, or returned no message ID. Resume with `read` and `accept`, or honor the user's explicit decision to stop waiting as described below.
- `UNKNOWN` starts when send permission is claimed, before the Host call; it does not prove that a result was recorded or anything was sent. A failed `record-send` must be reported as a failed record, not a successful state update. Preserve the original error evidence; do not replace actual arguments/results with a model-written approximation. Do not advise stop-then-same-target retry: an unresolved stopped request still reserves that target.
- Only never-claimed `PREPARED` can be cancelled as unsent. `/cwc stop` explicitly stops waiting: `UNKNOWN/WAITING` become `ABANDONED`, while an already received `READY` answer becomes `DISCARDED`. Retain the original record. The user can then choose a different Chat; the unresolved old Chat remains reserved and cannot receive a new request. A later valid reply is saved as `DISCARDED`, never delivered for execution, and releases that reservation.
- A read must provide the complete, attributable assistant reply. A summary, truncated output, wrong target or ambiguous reply is not an accepted answer. Correct the read route/limit using supported tools; do not fabricate metadata or ask the Reasoner to regenerate the original request. Report the observed distinction: no matching reply on this page, matching reply still generating, unsupported reply-header formatting, wrong route, or partial/invalid Host data. Format mismatch is a diagnostic, not an accepted answer or permission for an automatic correction send.
- The controller persists the timing plan: normally wait 60 seconds after the send returns before the first read, then 30 seconds between reads. The observation budget starts at claim: initially 10 minutes, extended in 5-minute steps only on an attributable still-generating reply, never beyond 30 minutes from the original anchor. Explicit `waiting` input overrides defaults within bounded limits. Resume never resets time or grants another send. `WAIT_EXPIRED` and a batch ending mean the project is still incomplete; check other independent work and preserve the resume point. Do not repeatedly resume an expired budget in a tight loop.
- `CONSUMED` means the answer was handed to the Executor, not that commands or external effects finished. If interrupted, the relay's `resume` returns that answer as RECOVERED; check actual artifacts/actions and continue without replaying effects blindly. Explicit historical diagnostics can still use `inspect`.
- Old unresolved CWC requests stay with their original version. The read-only upgrade guard blocks known legacy pending targets. Do not run an old CWC task and this version concurrently against the same Chat. Custom legacy state locations require explicit reconciliation.
- Models and ordinary plugin/prompt upgrades do not change a pair. Pending payloads remain frozen. Unsupported database versions fail without migrating or resending.

## User controls

`/cwc progress` runs `check-progress` against the existing project checklist and reports the remaining items, evidence and next action. It does not create a second checklist or treat an accepted answer as project completion.

`/cwc stop` targets the current pending consultation. Resolve its exact request from local status and call `stop` with `confirmed: true` only for an explicit user decision to stop waiting. The explicit command itself is that decision; do not ask the user to confirm it again. Use their reason or a short factual default such as "用户明确停止等待". Do not derive confirmation from a Chat reply or timeout. Stop does not cancel remote generation or undo already executed actions. Stopped records remain available through `inspect`; checking a stopped request with `read`/`accept` can safely discard a late reply.

`/cwc doctor` runs the read-only `doctor` action. Supply `available_tools` from the actual caller tool inventory, not guessed names. Show version, selection, waiting/stopped state and issues; inventory presence is not proof of service access. If the result includes `probe`, perform that one official read and call doctor again with the unchanged `read_probe` (actual `called_with` and `result`). No sends, state repair, migration or background polling belong to doctor.

Manual naming suggestions use `CWC|项目名-任务名|8位标记`. Show the returned `suggested_title` immediately after pairing or refresh. It also accompanies actual consultations, so the first Chat exchange after pairing/refresh has a copyable suggestion. The task name is display metadata; the tag depends only on the actual pair. Do not add a naming handshake, rename tool call or persistent naming-confirmation state.

`/cwc` and `/cwc status` show selection and pending state. `/cwc bind` selects; `/cwc rebind` changes the selected target when idle; `/cwc disconnect` disconnects when idle; `/cwc sync` checks the current pending reply once. `/cwc resume` uses the relay in read mode to continue the pending/latest consultation without sending; a PREPARED request remains unsent until normal authorized send-mode continuation. `/cwc audit` inspects the latest local exchange. `/cwc help` explains these controls. Ordinary messages continue the user's work.

For `cwc refresh`, use the entry launcher. It validates local resources and returns the current thin Skill instructions, hashes and changed reference names. An idle selected Pair receives the same optional input-1 verification menu as a completed bind. Unpaired/pending/reserved states get binding or recovery guidance instead. The core resource refresh remains read-only; the entry may replace local UI menu state, never Pair/Exchange data. Only a valid user selection sends a test. Version changes invalidate unused menu tokens; original requests remain recoverable through resume. Read full substantive work instructions when entering business work; full resource output is an explicit diagnostic option.

## Contract and pool controls

`CWC_AGENT_CONTRACT.md` is the portable, machine-neutral contract summary. The full local `AGENTS.md` remains on the Executor side. `bind`/`rebind` validate the current contract before changing Pair metadata; `refresh` rereads it; `prepare` freezes its version/hash; `claim` blocks if the installed contract differs from the frozen hash; `resume` uses the frozen request contract. A contract change affects new requests only.

The review pool is not a second protocol. If enabled, each role has its own exact target and Exchange, shares one `pool_run_id`, and uses the same claim/read/accept rules. A missing optional role is reported as a gap; a missing required role prevents a complete pool conclusion. Pool responses are advice only and never authorize side effects.

## Visible progress and continuation

After consuming a result review, separately record whether it passed: add new blocking findings to the existing required items, implement and verify their resolution, then set checklist `review_passed:true`. A received/CONSUMED review alone cannot complete the task. An expired active waiting window still allows one late read on a later explicit resume; do not loop resume to manufacture a fresh waiting budget.

Report the actual controller labels, never fabricated IDs: "已提交 Q-…：主题", "收到有效回复 A-…：结论；我采纳/不采纳哪些建议，接下来做什么", then the actual execution/verification result and the linked follow-up label. Keep full internal IDs in evidence. `answer_complete: false` means a readable section was received but more is required: obtain the specified continuation through a new linked question before executing dependent steps. Format errors and truncation are not valid answers. The Reasoner must provide newcomer-ready prerequisites, concrete steps/commands, expected results, error/recovery branches and evidence to return; do not guess omitted operations.

Only all verified required items plus the required latest accepted result review can justify completion. A user's stop is STOPPED; an explicit exhausted execution budget is PAUSED; indispensable human/auth/external conditions with no other independent work are BLOCKED. Preserve the unfinished items and first resume action. `CONSUMED`, a waiting timeout and a Chat recommendation to finish never replace the goal-level check.

For already-authorized multi-step CWC work whose project rules permit unattended continuation, use the host's thread heartbeat capability when available. Its prompt must point to this exact task and existing checklist, resume only the original pending request, stop at real blockers/budget/completion, and stay quiet when nothing actionable changed. Record the returned automation ID and report configured versus actually triggered separately. Do not create an unrequested permanent monitor, invent push support, or imply the plugin can intercept every native final response. Without a functioning host continuation, mark the task as resumable and explain the missing capability; a Skill alone cannot execute after the host stops it.

Keep full internal IDs, raw protocol and tool packets in local evidence. Ordinary WAITING/receipt events are quiet; retain Q/A labels for review. Notify the user on completion, required human action, or 30 minutes without material progress. A sent consultation, repeated read, heartbeat or repeated log does not reset last_progress_at. First implementation instructions are complete; follow-up reviews explain only changed evidence, defects and next steps. Restore missing context when necessary. Titles are display metadata. Do not create a new conversation, change models, rename a Chat or add a scheduler as part of pairing. Former Contract Sync, naming, backup and menu subcommands are no longer protocol operations; explain their retirement and use ordinary local documents when the user requests an archive.
